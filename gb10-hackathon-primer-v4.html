1.What is the GB10?

The GB10 is the NVIDIA Grace Blackwell superchip inside the Dell Pro Max with GB10 — a desk-side AI workstation. The headline spec is 128 GB of unified memory, shared between the CPU and GPU, which is what lets it run large AI models that a normal laptop can't fit.

  • It runs large language models (LLMs) locally — no cloud, no internet required, no per-token cost.
  • Your data stays on the machine (privacy) and there's no network latency.
  • It's the "computer that thinks" you'll be building on during the hackathon.
Bottom line: the GB10 is a powerful local-AI box. You'll interact with it through the terminal, a model server like Ollama or vLLM, and tools like Hermes.

2.LLM basics: tokens, context, temperature

Three concepts make everything else click:

  • Tokens — the chunks of text a model actually reads and writes. Roughly, 1 token ≈ ¾ of a word (a token can be a word, part of a word, or punctuation). Models count their work in tokens.
  • Context window — how much text the model can "see" at once (measured in tokens). If you go over it, the model forgets the oldest part. The GB10 can hold a large context window for long documents.
  • Temperature — the "randomness" dial. 0 = deterministic (same input, same output — good for code and facts); higher values (0.7–1.0) = more varied/creative (good for brainstorming and writing).
Speed matters too: you'll see "tokens per second" (tok/s). Higher is snappier. Local models report this so you can compare how fast different models feel.

3.What is a Docker container?

A container is a lightweight, isolated package that bundles an application with everything it needs to run — code, libraries, dependencies, settings — into one portable unit. It runs the same way on the GB10, your laptop, or a server.

Analogy: think of a shipping container. Whatever's inside, it's a standard box that fits on any ship, truck, or crane. A Docker container does the same for software.

Key vocabulary:

  • Image — the blueprint (a snapshot of the app + dependencies). You build it once.
  • Container — a running instance of an image.
  • Dockerfile — the recipe that defines how to build an image.
  • Registry — a library of pre-built images (like Docker Hub) you can pull from.

Why it matters here: you can run a model server (like vLLM) or an entire app in a container, and it behaves identically everywhere — no "works on my machine" problems.

# Pull an image
docker pull <image>

# Run a container from it
docker run -d --name myapp <image>

# See what's running
docker ps

# List images you have
docker images

# Run a command inside a running container
docker exec -it myapp bash

4.What is a Python virtual environment?

A virtual environment ("venv") is an isolated copy of Python for one project, so its packages don't clash with other projects. If project A needs version 1.0 of a library and project B needs 2.0, two venvs keep them separate.

# Create a venv called "venv"
python -m venv venv

# Activate it (Linux / macOS)
source venv/bin/activate

# Activate it (Windows)
venv\Scripts\activate

# Install packages (now scoped to this venv)
pip install <package>

# Leave the venv
deactivate
Rule of thumb: one venv per project. Activate it before installing or running anything, and you'll never have "but it worked yesterday" dependency conflicts.

5.Jupyter Notebooks

A Jupyter Notebook is an interactive, browser-based document for running Python in small chunks called cells. Each cell holds code or formatted notes (markdown), and the result — text, a chart, a table — appears right below the code. That makes it ideal for exploring data and AI models, and for showing your work.

Why it matters here: it's the fastest way to call a model, inspect the output, tweak it, and visualize results — all in one live, shareable document.

Installing + launching

# In your project's venv
pip install jupyterlab

# Launch it (opens a browser tab)
jupyter lab

The basics

  • Cells — a notebook is a stack of cells. Code cells run Python; Markdown cells are for notes and headings.
  • Run a cell — Shift+Enter runs the current cell and moves to the next. Output appears just below it.
  • Variables persist — a variable defined in one cell is available in the next, so run cells top-to-bottom (order matters).
  • Kernel — the live Python process behind the notebook. Restart it (Kernel → Restart) to clear all state.

Two handy tricks

# Run shell commands from inside a cell by starting with ! or %
%pip install requests

# A variable on its own line prints its value:
x = 3 + 4
x     # → 7
Typical flow: one notebook per experiment — load the model call in one cell, tweak the prompt in the next, chart the result below. Then share the .ipynb file with your team.

6.Basics of prompting

A prompt is the instruction you give an LLM. The quality of your prompt directly shapes the quality of the answer. Good prompting is a skill you'll use constantly.

Five things that improve results:

  • Be specific. "Write a Python script that reads a CSV and prints the average of column 'score'" beats "analyze my data."
  • Give context. Tell the model what you're doing and why — it has no other context about you.
  • Show examples. Give one or two input→output examples ("few-shot") so it matches your format.
  • Specify the output format. "Respond as a JSON object with keys …" or "use bullet points."
  • Iterate. Treat the first answer as a draft. Ask it to refine, shorten, or fix a specific part.

Two extra techniques:

  • System prompt — a standing instruction ("You are a helpful tutor who explains in plain English") that frames the whole conversation.
  • Chain-of-thought — asking the model to "think through this step by step" improves reasoning on harder problems.
What NOT to do: vague one-word requests and assuming the model knows your intent. It's powerful but it can't read your mind — clarity is on you.

7.Working with local models

A local model is an LLM running on your own hardware (the GB10) instead of in the cloud. Instead of sending your text to an API over the internet, it runs right on the box.

Why local:

  • Privacy — your prompts and data never leave the machine.
  • No per-token cost — free to experiment, no API bill.
  • Works offline — no internet needed once the model is downloaded.
  • Full control — you pick the model, the quantization, the settings.

How it works: a model server (Ollama is the easy one; vLLM is the high-performance one) loads a model file and exposes a local API. You talk to it with a chat UI or by calling that API from your code. The next section compares the main servers.

Terms you'll hear:

  • Model weights — the learned parameters of the model (the file you download).
  • Quantization — compressing the weights (e.g. 4-bit) to use less memory, at a small cost to quality.
  • Tokens/sec — how fast the model generates.
# With Ollama — pull a model, then chat
ollama pull qwen3.8:27b
ollama run qwen3.8:27b

8.Model servers: Ollama, LM Studio, vLLM

A model server loads a model into memory and exposes an API so you (or many users at once) can send it requests. Three common choices do the same core job — the difference is ease vs. speed.

ServerBest forHow it runs
OllamaQuick local use, one model, easy setupllama.cpp under the hood; GGUF models; ollama run
LM StudioDesktop GUI — browse, download, chatAlso llama.cpp-based; point-and-click, no terminal
vLLMHigh-throughput serving, many concurrent usersCustom engine tuned for NVIDIA GPUs; HTTP server

Ollama is the easiest path and perfect for one person. LM Studio is a friendly desktop app for trying models visually. vLLM is the performance choice — built to serve many requests at once as fast as the GPU allows, which matters the moment more than one person shares the box.

Why vLLM is fast on NVIDIA hardware like the GB10:

  • Continuous batching — instead of one request at a time, it packs many together and runs them through the GPU in parallel. Under load, this is the biggest single win.
  • PagedAttention — manages the model's memory (the "KV cache") in small pages, wasting less and fitting longer contexts.
  • NVIDIA-native quantization — supports high-efficiency formats like FP8 and (on Blackwell) NVFP4, packing the model smaller to run it faster on the GB10's GPU.
  • Optimized kernels — fused CUDA operations tuned specifically for NVIDIA GPUs.

Net: for a single user, Ollama and vLLM feel similar. For a hackathon where a team shares one GB10, vLLM keeps everyone responsive at once instead of queueing.

# Serve a model with vLLM (OpenAI-compatible API on port 8000)
vllm serve Qwen/Qwen3-8B --port 8000

# Call it from your code — same shape as Ollama, just a different URL
curl http://localhost:8000/v1/chat/completions [localhost] \
  -H "Content-Type: application/json" \
  -d '{"model": "Qwen/Qwen3-8B",
       "messages": [{"role":"user","content":"Hello!"}]}'
Rule of thumb: start with Ollama to get a model running in seconds; reach for vLLM when you need speed under load, or want to squeeze the most performance out of the GB10.

9.Basics of Hermes / Hermes Desktop

Hermes is an AI agent framework. Where a plain LLM only talks, an agent can act — it can run terminal commands, read and write files, search the web, and chain those actions to finish a multi-step task.

  • Chat — ask it questions like any assistant.
  • Tools — it can run commands, edit files, browse, and more, then reason over the results.
  • Memory — it can remember context across a session.
  • Skills — reusable procedures it's learned.

Hermes Desktop is the graphical app (vs. the terminal). Same agent, friendlier UI — type in a chat, watch it work, see what tools it's using.

For the hackathon: treat Hermes as a coding + research partner. Give it a concrete task ("scaffold a FastAPI endpoint that does X"), watch what it does, and correct it. The loop of instruct → observe → correct is the core skill.

11.Monitoring the GPU with nvidia-smi

nvidia-smi (NVIDIA System Management Interface) is the command that tells you what your GPU is doing right now. On the GB10 it's the fastest way to confirm your model is actually using the chip — and whether the GPU is the bottleneck.

What it's for

  • Confirm the GPU is present and healthy — the first check after booting.
  • See GPU utilization — how busy the chip is (0% = idle, near 100% = working flat out).
  • See memory usage — how much of the GPU's memory is in use, and total available.
  • See what's using it — which processes (Ollama, vLLM, Python) are on the GPU.
  • Check temperature and power — mostly for diagnostics.

The basic command

nvidia-smi

It prints a table with the GPU name, Utilization (GPU compute and memory), Memory-Usage (used / total), Temperature, and a list of running processes with how much memory each holds.

Watch it live

# Refresh every 1 second (Ctrl+C to stop)
nvidia-smi -l 1

# One-time snapshot with just the numbers you care about:
nvidia-smi --query-gpu=utilization.gpu,memory.used,memory.total,temperature.gpu --format=csv

Reading the key numbers

  • GPU-Util — % of GPU compute in use. 0% = idle. A model actively generating sits near 100%. Low % while a model feels slow means the bottleneck is elsewhere (memory, CPU, or the model is just small).
  • Memory — used vs. total. Each loaded model reserves a chunk of memory; this is how you tell whether a model fits or an old one is still loaded.
  • Processes — one line per program using the GPU. Use it to find a "stuck" process after you've stopped a server.
Practical habit: run nvidia-smi before and after starting a model — memory will jump once it's loaded, and GPU-Util climbs while your prompt is generating. That proves it's really on the chip.
Why it matters at a hackathon: when a model is slow or errors, nvidia-smi is the first diagnostic — is it memory (model doesn't fit), utilization (something else is hogging the GPU), or empty (the model never loaded)?

12.SSH: connect to the GB10

SSH (Secure Shell) is the way you securely control another computer over the network — from your own terminal. You type commands on your laptop, but they execute on the GB10, and everything you send is encrypted.

How it works: you run ssh user@address; the GB10 verifies who you are (a password or an SSH key), then opens a secure channel. From then on, your terminal is effectively "inside" the GB10 — run a model, edit a file, start a server, all remotely.

1. Set up the GB10 (server side)

# On the GB10, install and start the SSH server
sudo apt install openssh-server
sudo systemctl enable --now ssh

# Find the address and username you'll connect with
hostname -I    # the IP address (e.g. 192.168.1.10)
whoami         # the username (e.g. gb10)

2. Connect from your own device (client side)

Linux and macOS ship ssh built in. On Windows 10/11, open PowerShell or Windows Terminal (the OpenSSH client is included).

# Connect — you'll be prompted for the GB10's password
ssh username@IP-address

# Example
ssh gb10@192.168.1.10

3. (Optional) Key-based login — skip the password every time

# On YOUR device, generate a key pair (accept the defaults)
ssh-keygen

# Copy your public key to the GB10 (enter its password one last time)
ssh-copy-id username@IP-address

# From now on, ssh connects without a password
ssh username@IP-address
Why keys beat passwords: a key can't be guessed, you don't retype a password, and it's required for scripts and automation that connect unattended.
In practice: SSH is how you'll drive the GB10 from your laptop — run a model, start a server, check nvidia-smi — all from your own machine, without a monitor or keyboard on the box itself.

13.Git basics

Git is version control — it tracks every change to your code so you can collaborate and never lose work. You'll want it for team projects.

# Copy a repository to your machine
git clone <repo-url>

# Stage + commit your changes
git add .
git commit -m "describe what you changed"

# Share with the team / get their changes
git push
git pull

# Work on a separate branch
git checkout -b my-feature
Golden rule: commit often with clear messages. It's your safety net — if you break something, you can always get back to a working version.

14.Calling a local model (API)

Once a model is running locally, your code talks to it over a local HTTP API — the same "chat" format as OpenAI, but pointing at your own machine instead of the cloud.

# Ollama's local endpoint (OpenAI-compatible)
curl http://localhost:11434/v1/chat/completions [localhost] \
  -H "Content-Type: application/json" \
  -d '{
    "model": "qwen3.8:27b",
    "messages": [{"role": "user", "content": "Hello!"}]
  }'

That's the whole trick: you're swapping a cloud URL for localhost. Any "call an LLM" tutorial works the same, just with your local model name and port (Ollama uses 11434; vLLM defaults to 8000).

15.15-minute warm-up: prove the stack works

Before the event kicks off, spend 15 minutes on this once. If every step works, your environment is ready — and you'll have your first local model call behind you.

  1. Connect to the GB10 — ssh user@ip (see the SSH section).
  2. Confirm the GPU is alive — run nvidia-smi; it should list the GB10's GPU.
  3. Pull and start a model — ollama pull qwen3.8:27b, then ollama run qwen3.8:27b.
  4. Run one prompt — type a question, press Enter, confirm a sensible answer. Type /bye to exit.
  5. Call the API from the terminal — the curl example in "Calling a local model," pointed at localhost:11434.
  6. (Optional) Call it from Python — make a venv, pip install openai, send one request (below).
# On the GB10, in order:
ssh user@ip                 # 1 · connect
nvidia-smi                  # 2 · GPU present?

ollama pull qwen3.8:27b     # 3 · fetch the model
ollama run qwen3.8:27b      #    · chat — type a question, /bye to exit

curl http://localhost:11434/v1/chat/completions [localhost] \
  -H "Content-Type: application/json" \
  -d '{"model":"qwen3.8:27b","messages":[{"role":"user","content":"Say hi!"}]}'
# Optional Python version (inside a venv):
from openai import OpenAI
client = OpenAI(base_url="http://localhost:11434/v1 [localhost]", api_key="local")
r = client.chat.completions.create(
    model="qwen3.8:27b",
    messages=[{"role": "user", "content": "Say hi!"}],
)
print(r.choices[0].message.content)
All six working? You're fully set up — the rest of the hackathon is building on this exact loop: prompt the model, read the output, call it from code.
